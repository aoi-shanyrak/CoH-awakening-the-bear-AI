## 📊 Что было изменено

### 1️⃣ **Структура `Action`** (action.hpp)
- Добавлено **13 флагов** типа `bool` для информации о модификаторах
- Флаги указывают на возможные варианты на уровнях 2-3 MCTS
- **Эффект:** Действие теперь содержит метаинформацию о своих модификаторах

### 2️⃣ **Генерация действий** (action_generation.cpp, action_generation.hpp)
- `getValidActions()` → `getBaseActions()` (переименование)
- **Убрано:** `Cards::addCardActions()` – создание вариантов с картами
- **Добавлено:** `Cards::fillCardFlagsForAction()` – заполнение флагов
- **Эффект:** Ветвление **снизилось с 500+ до 200-300** базовых действий

### 3️⃣ **Новый модуль `card_utils`** (card_utils.hpp, card_utils.cpp)
- 13 функций проверки применимости каждой карты
- `fillCardFlagsForAction()` – заполняет все флаги Action
- `hasCardInHand()` – вспомогательная функция
- **Использование:** В `getBaseActions()` и при расширении узлов MCTS уровня 3

### 4️⃣ **Новый модуль `MCTS`** (mcts.hpp, mcts.cpp)
- `MCTSNode` – структура иерархического узла с 4 уровнями
- `MCTSSearch` – класс с полным циклом MCTS
- UCB1 выбор для балансировки exploration/exploitation
- **Уровни дерева:**
  - Level::Base – базовые действия (~200)
  - Level::CAPs – варианты потрат CAPs (2-3)
  - Level::Card – применимые карты (2-4)
  - Level::Terminal – готовое действие

## 🎯 Ключевые изменения архитектуры

### Раньше (плоская структура):
```
getValidActions() 
  ├─ базовые действия (150)
  └─ Cards::addCardActions()
     ├─ Adrenaline варианты (50)
     ├─ CommandAction варианты (150)
     └─ ... другие карты
ИТОГО: 500+ действий в одном списке
```

### Теперь (иерархическое дерево):
```
getBaseActions()
  ├─ Базовые действия (200)
  │   └─ каждое заполнено флагами
  
MCTSSearch::runIteration()
  ├─ Уровень 1: выбираем базовое действие из 200
  ├─ Уровень 2: выбираем CAPs (0-2) из 2-3 вариантов
  └─ Уровень 3: выбираем карту из 2-4 вариантов
  
assembleFullAction(node)
  └─ собираем полное действие из пути дерева
```

**Преимущества:**
- ✅ Ветвление на каждом уровне: 200 × 3 × 3 ≈ 1800-3600 (вместо 500+)
- ✅ MCTS может глубже исследовать дерево
- ✅ Легче добавлять новые карты (просто новый флаг + проверка)
- ✅ Структура соответствует иерархии решений игрока

## 📈 Ожидаемый прирост производительности

### Теория MCTS:
- Глубокое дерево лучше для поиска
- Меньшее ветвление на каждом уровне = больше посещений каждого узла
- Больше посещений = лучшая оценка позиций

### Числа (приблизительно):
- **Раньше:** 500 действий × глубина 1-2 = сложно исследовать
- **Теперь:** 3 уровня × 200/3/3 = легче балансировать exploration/exploitation
- **Прирост:** может быть +30-50% качества ходов при той же глубине поиска

## 💡 Дизайн-решения

### Почему 4 уровня, а не 2?
- **2 уровня (Base + модификаторы):** плоское, много ветвей на каждом
- **4 уровня:** глубокое, MCTS может лучше исследовать
- **Результат:** UCB1 работает эффективнее на глубоких деревьях

### Почему `canSpendAdditionalCAPs` отдельный флаг?
- CAPs – универсальный модификатор, работает почти для любого действия
- Но НЕ работает для Stall и Pass
- Отдельный уровень позволяет явно контролировать эту механику

### Почему не просто добавить карты в getBaseActions?
- Взрывное ветвление: каждая карта создаёт новое действие
- MCTS нужна глубокая иерархия, не плоская структура
- Иерархия соответствует реальному процессу выбора игрока
